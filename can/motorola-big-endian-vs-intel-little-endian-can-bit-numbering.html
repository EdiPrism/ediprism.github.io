Motorola Big-Endian (@0 Sawtooth) vs. Intel Little-Endian (@1) CAN Bit Numbering

The #1 cause of silent automotive ECU signal corruption is mixing Intel Little-Endian (@1) LSB start bits with Motorola Big-Endian (@0) MSB sawtooth bit numbering inside the same 64-bit or 512-bit CAN FD payload.

1. Standard CAN Byte & Bit Grid Indexing (0..63)

Within every CAN payload byte B (0..7 for Classic CAN, 0..63 for CAN FD), bits are numbered 0..7 from LSB (right) to MSB (left): flatBit = B * 8 + bitInByte.

Byteb7 (MSB)b6b5b4b3b2b1b0 (LSB)
Byte 076543210
Byte 115141312111098
Byte 22322212019181716

2. Intel (@1) Contiguous Upward vs. Motorola (@0) Sawtooth Step

  • Intel Little-Endian (start|len@1+): start is the LSB; bits advance monotonically upward start .. start + len - 1. Example: 24|16@1+ occupies bits 24..39 (Byte 3 LSB → Byte 4 MSB).
  • Motorola Big-Endian (start|len@0-): start is the MSB; each step moves toward bit .0 of the current byte, then jumps +15 to bit .7 (MSB) of the next byte:
nextMotorolaBit(b) = (b % 8 == 0) ? (b + 15) : (b - 1)
Classic Firmware Bug: 15|16@0- Colliding with 16|8@1+! A developer sees SG_ RequestedTorque : 15|16@0- and assumes it occupies bits 0..15 (Bytes 0..1). In reality, starting at bit 15 (Byte 1, b7) steps down 15..8 (Byte 1), then jumps +15 to bit 23..16 (Byte 2) — colliding head-on with SG_ BrakePedalPct : 16|8@1+ on all 8 bits of Byte 2!

Frequently Asked Engineering Questions

How does AUTOSAR ARXML PACKING-BYTE-ORDER map to DBC @0 and @1?

AUTOSAR MOST-SIGNIFICANT-BYTE-FIRST maps to Motorola Big-Endian (@0) where START-POSITION specifies the MSB, whereas MOST-SIGNIFICANT-BYTE-LAST maps to Intel Little-Endian (@1) where START-POSITION specifies the LSB.
